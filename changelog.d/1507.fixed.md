- **Merge retries accept PR checkpoints at s10 across runs on the same head, and refusals suggest resolving commands** (#1507):
  - `keel merge` accepts an unmerged checkpoint at `s10` for the PR across run IDs when its recorded head SHA matches the PR's current head (and matches `accepted_run_ids` when `--run-id` overrides the gates-pass run, refusing anonymous checkpoints when restricted).
  - Upon landing, `keel merge` adopts the covering checkpoint (`adopt: true`, failing closed with `checkpoint changed since the gate; adoption refused` if the reread checkpoint's source `run_id`, `pull_request`, or `head_sha` provenance changed or is missing, or if `state.merge` is already `merged` or `pending`) and records provenance in `carried_from_run_id` across later same-run updates.
  - Checkpoints already marked `merged` (`already-merged`, naming `keel resume ...`) or `pending` (`in-flight`, naming `keel checkpoint ... --write ... --merge-state failed`), or from earlier/missing heads (`stale-head`), are refused; same-run `--write` updates preserve existing checkpoint fields when omitted.
  - Refusals for missing gates-pass records, missing run IDs, missing checkpoint files, and stale-step checkpoints print safely-quoted recovery commands (`keel ship` omits `--run-id` and `--capture-status` so unedited execution fails fast, `missing` and `stale-step` include `valid only if the run genuinely reached s10`, and foreign-run checkpoint refusals omit `--write`).

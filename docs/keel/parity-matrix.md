# Legacy-to-keel command parity matrix

This matrix tracks whether a project can replace a legacy workflow command with the
corresponding `/keel:<command>` adapter without losing behavior.

The migration target is:

- legacy command wrappers become thin calls into keel after their row is marked
  `parity-proven`.
- keel-owned behavior lives in core runtime, transport, planning, adapter, or backbone
  contracts.
- project-owned behavior lives in `.keel/project.yaml`, project policy packs,
  `.keel/extensions/`, or project-provided commands.
- no consumer project policy is copied into packaged keel command bodies.

## Status vocabulary

| status | meaning |
|---|---|
| `not-started` | The row is documented, but parity work has not started. |
| `in-progress` | The owning issue is actively reducing known gaps. |
| `blocked` | The row cannot progress until a listed dependency ships. |
| `parity-proven` | The legacy behavior is represented by keel core, runtime, policy, extensions, adapters, or wrappers, and the row has evidence. |
| `deferred` | The gap is intentionally not being migrated yet, with a documented reason. |

## Update rules

- Keep the columns stable so each owning issue can update its row without changing the
  matrix structure.
- Every known gap must link to at least one GitHub issue.
- When a row reaches `parity-proven`, add evidence in the row rather than deleting its
  history.
- If a behavior is intentionally not migrated, mark the row or specific gap `deferred` and
  link the deferral rationale.
- Do not add consumer project names, private paths, product policy, path globs, or
  project-only commands to this document.

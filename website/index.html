keel ⚓

Keel turns coding agents into work owners. From issue intake to implementation, review, safe merge, closure, and capture hooks.

100% line + branch coverage one-command setup stdlib-first · 1 runtime dep Python ≥ 3.11 📊 coverage report → GitHub →

What it is

keel is a ship's backbone — the fixed spine every project builds on. It models the work pattern of a strong teammate: decide whether an issue is ready, own the implementation, get it reviewed, keep quality gates green, merge inside policy, close the loop, and leave useful memory behind. The same flow runs whether the coding agent is Claude Code, Codex, Gemini or Antigravity; projects never fork the backbone, they only:

① set values

A small .keel/project.yaml: package core range, base branch, gates, capabilities, workflow policy, health sources, and path globs.

② snap in Lego

Add-only extensions into every backbone step hook plus policy_pack data for labels, local commands, reports, and review rules. The backbone stays fixed.

How it compares

Keel is not just a coding agent, PR reviewer, or merge queue. It connects those pieces into one issue-to-done ownership loop.

Quickstart

Set up a consumer repo in one pass

keel setup --root .
# writes .keel/project.yaml when missing
# installs .claude/commands/keel/*
# installs .agents/skills/keel-*
# strict-validates config + extensions
# renders the resolved backbone plan

See what ship would do, right now

keel ship .keel/project.yaml --root .
# keel ship — myapp  (base main)
#   risk tier     : TIER-3  → 3 reviewer(s)
#   merge window  : OPEN
#   gate build          ok
#   gate lint           ok
#   decision      : MERGE — clear to merge

keel sync does not install the latest PyPI package. Upgrade keel-workflow with pipx upgrade keel-workflow or python -m pip install --upgrade keel-workflow, then run keel sync --dry-run and keel sync. Sync only updates marker-protected generated adapter files; project config and extensions are validated afterward, never rewritten.

Claude plugin

The repository now includes a Claude plugin manifest and a keel-onboard skill. The plugin does not fork the command bodies; it teaches Claude Code to run keel setup, verify .keel/project.yaml, and keep project behavior in policy packs or extensions. The generated adapters remain the runtime surface for actual /keel:<command> work.

Configuration reference

A Keel consumer is configured with values, not copied command bodies. Top-level fields choose the core version, repository, base branch, timezone, merge window, built-in gates, extension directory, and add-only extension hooks. knobs declares runnable commands, risk globs, docs paths, CI workflow mapping, local agent roles, and runtime capabilities. policy_pack is durable project-owned data for labels, lifecycle transitions, risk rules, test groups, docs policy, health providers, scan scope, local project commands, workflow policies, report destinations, and review rubric additions.

Every field and nested parameter is documented in docs/keel/configuration.md. Unknown keys are rejected by the bundled schema, so the reference is intentionally strict.

Workflow commands (/keel:<command>)

17 agentic workflows ship with the package. keel install-adapter claude installs native Claude commands; keel install-adapter skills installs one shared skill set under .agents/skills/keel-<command>/ that every non-Claude agent (Codex, Antigravity, Gemini) reads. Each is project-neutral — behaviour comes from that repo's .keel/project.yaml. Full reference: docs/keel/commands.md.

commandwhat
/keel:shipdrive an issue end-to-end (select → branch → implement → CI → review → test → merge → close) — per-round review, inline comments, delegation, jury gate, merge window + lock, attribution; --compound selects the compound-engineering profile that reuses the same backbone with documented s4/s7/s9/s11 step overrides
/keel:implementdelegate one issue to the right implementer; the s4 implement step standalone
/keel:review-cyclemulti-reviewer review→fix cycle over open PRs (parallel reviewers, capped fix rounds); does not merge
/keel:pr-loopiterate an open PR's review comments + CI to green, then hand off to the windowed merge
/keel:review-all-daytime-window diff-review sweep; open one issue per serious finding (read-only otherwise)
/keel:regressioncodebase-wide regression scan via parallel per-area subagents; open fix issues, route to ship
/keel:triageauto-classify unlabelled issues (role/priority/status) via a classifier subagent
/keel:morningmorning briefing — deferrals, shipped-since, health signals, ranked focus list
/keel:overnightunattended overnight block — run ship over the queue until the merge window closes
/keel:wrapfinish a session — run gates, commit, push, open a PR, record a recap
/keel:ci-checkcheck the latest CI run; on failure diagnose root cause + propose one fix (no auto-apply)
/keel:coverageper-PR coverage delta (base→head); flag low-coverage × high-risk hot spots
/keel:deps-auditdependency security + licence audit; classify and route fixes to ship
/keel:flake-auditdetect intermittently-failing tests from CI history; open one issue per new flake
/keel:stale-prsfind quiet/drifted PRs; triage, comment, optionally rebase (respecting the window)

Runs on the free runner

The keel-ship GitHub Action runs keel against every PR on GitHub's free hosted runner — using the runner's own git + gh — and posts the assessment as a comment. This very site & its coverage report are built and deployed the same way.
